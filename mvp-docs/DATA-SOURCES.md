# KanjiForge — Data Sources & Licensing

Every byte KanjiForge ships must have a documented, verified, compatible open license. This document is the inventory, the extraction plan, and the honest account of what we **cannot** have.

> **Verify before shipping.** License terms and file locations change. Re-check each upstream source at build time and fail the pipeline if a license file hash changes unexpectedly.

## 2. EDRDG files — the backbone

**KANJIDIC2, JMdict, JMnedict, KRADFILE/RADKFILE** are all maintained by the Electronic Dictionary Research and Development Group (Jim Breen et al., Monash University) and released under **Creative Commons Attribution-ShareAlike 4.0**.

Practical consequences of CC BY-SA 4.0 for us:

1. **Attribution is mandatory and must be visible**, not buried in a repo file. Ship an in-app "Data sources" screen (reachable from Settings → About) listing each source, its author, its license, and a link. Also ship `ATTRIBUTION.md` in the repo.
2. **ShareAlike propagates to the data, not the code.** Our derived content packs — the transformed SQLite/JSON files — are adaptations and must themselves be distributed under CC BY-SA 4.0. Publish the pack build scripts and the packs under CC BY-SA 4.0 explicitly. The application source code is a separate work and can carry its own license (see PRD §9 open question 1).
3. **No additional restrictions.** We cannot DRM the packs or forbid redistribution.

### 2.1 What we extract from KANJIDIC2

Per character:
- `literal` — the kanji itself
- `codepoint` — Unicode
- `radical` — classical (KangXi) and Nelson radical numbers
- `misc/grade` — 1–6 elementary, 8 = remaining jōyō, 9–10 = jinmeiyō
- `misc/stroke_count` — including alternate counts
- `misc/freq` — newspaper frequency rank (1–2500)
- `misc/jlpt` — **legacy 1–4 scale only**; see §5
- `reading_meaning/rmgroup/reading` — `ja_on`, `ja_kun` (keep okurigana dots and `-` prefix markers, render them properly)
- `reading_meaning/rmgroup/meaning` with `m_lang="en"` — English glosses
- `reading_meaning/nanori` — name readings

**Explicitly strip:** all `query_code` entries with `qc_type="skip"` and `qc_type="misclass"`. See §6.

Optionally keep for a "reference" pack: Four Corner codes, Nelson/Halpern/Heisig dictionary index numbers — but check each contributor's terms in the EDRDG license page before shipping; several are contributed under their own conditions.

### 2.2 What we extract from JMdict

Per entry:
- `k_ele/keb` — kanji writings, with `ke_inf` (irregular, outdated) and `ke_pri` (news1, ichi1, spec1, gai1 — the commonality markers)
- `r_ele/reb` — kana readings, with `re_nokanji`, `re_restr`, `re_pri`
- `sense/pos` — part of speech
- `sense/gloss` (English only for MVP; the multilingual glosses have separate contributor terms)
- `sense/misc` — usually-kana, colloquial, archaic
- `sense/field`, `sense/dial` — domain and dialect
- `sense/stagk` / `stagr` — sense restrictions

**Commonality ranking:** derive a single `commonScore` from the `*_pri` tags (`news1`/`ichi1`/`spec1` ≫ `news2`/`ichi2` ≫ none). This drives search result ordering and the "Top N words" decks. Do it once at build time.

### 2.3 Tiering the dictionary

Full JMdict + JMnedict is far too much to force on a phone. Ship three packs:

| Pack | Contents | Size (compressed) | Default |
|---|---|---|---|
| `words-core` | Entries with any `*_pri` tag (~30k entries) — covers essentially all study vocabulary | ~6 MB | Installed by default |
| `words-full` | All ~200k JMdict entries | ~25 MB | Optional |
| `names` | JMnedict (~700k entries) | ~15 MB | Optional |

`words-core` alone must be enough for every study feature, every built-in deck, and import enrichment. `words-full` and `names` only extend dictionary search depth.

## 3. KanjiVG — stroke order

**License:** Creative Commons Attribution-ShareAlike 3.0. Copyright Ulrich Apel.
**Repo:** the KanjiVG project's GitHub releases (grab a tagged release, not `main`, so builds are reproducible).

Contains SVG path data for ~6,500+ characters, with each `<path>` carrying:
- `kvg:type` — the stroke's calligraphic type (e.g. `㇐`, `㇑a`)
- Grouped `<g>` elements with `kvg:element`, `kvg:radical`, `kvg:position`, `kvg:phon` — this is a **component decomposition tree**, which is far more valuable than the strokes alone.

### 3.1 Three separate derived assets

1. **Stroke paths** — the ordered list of SVG path `d` strings per character, normalized to a 109×109 viewBox. Used for animation *and* for stroke-order validation matching. Store as a compact JSON array; do not ship the original SVG files.
2. **Stroke start points** — precomputed first point of each path, so the writing trainer can hint without parsing SVG at runtime.
3. **Component decomposition** — a parent/child tree of `kvg:element` values per character. Powers "elements" in the detail view and feeds the similar-kanji generator (§7).

### 3.2 Attribution requirement

CC BY-SA 3.0 requires attributing Ulrich Apel and indicating changes. Our normalization *is* a change. State it: *"Stroke data derived from KanjiVG by Ulrich Apel, CC BY-SA 3.0. Paths normalized and re-encoded."*

### 3.3 Compatibility note

KanjiVG is CC BY-SA **3.0**; EDRDG data is CC BY-SA **4.0**. CC BY-SA 3.0 material may be used in a 4.0 adaptation (4.0 is a listed compatible license for one-way upgrade), but keep the two datasets in **separate pack files** with separate license statements. Do not merge them into one blob with one ambiguous license header.

## 4. Sentences and furigana

### 4.1 Tatoeba

**License:** CC BY 2.0 FR for the sentence corpus. Includes the Tanaka Corpus JA-EN pairs that most Japanese tools use.

Extract: the `sentences.csv` + `links.csv` exports, filtered to Japanese sentences with at least one English translation. Additionally use Tatoeba's indices file (the WWWJDIC-style `examples.utf` format) which annotates which JMdict sense each word maps to — that's what enables "show me example sentences for *this* meaning of this word."

Filter aggressively:
- Length 6–30 characters (too short is useless, too long is intimidating on a phone)
- Prefer sentences whose vocabulary sits at or below the target word's difficulty
- Cap at ~5 sentences per word, ranked by a simple readability score
- Manually spot-check for inappropriate content — Tatoeba is user-contributed and contains some odd material

CC BY 2.0 FR requires attribution but **not** share-alike, so this pack has looser terms than the EDRDG ones. Still ship it separately with its own attribution.

### 4.2 JmdictFurigana

**Source:** the JmdictFurigana project (Doublevil), which maps JMdict `(kanji-writing, kana-reading)` pairs to per-character furigana alignments.

This solves a genuinely hard problem: given 食べ物 / たべもの, knowing that 食→た, べ, 物→もの. Do not attempt to derive this yourself; the edge cases (rendaku, jukujikun, ateji) are brutal.

Verify the current license on the repo before shipping. Audit note (T0.1): the GitHub repo root contains an explicit MIT LICENSE file (hash c7d0d41a... of its body), which applies to the repository code. The published alignment data is derived from JMdict and therefore retains JMdict's CC BY-SA 4.0 obligations; record both the code and data provenance in shipped attribution.

## 5. JLPT level data — the honest problem

**There is no official JLPT vocabulary or kanji list.** The Japan Foundation stopped publishing them when the test was revised to N1–N5 in 2010. KANJIDIC2's `jlpt` field is the **old 4-level (1–4) scale** and is not directly convertible.

Options, in order of preference:

1. **Use an openly-licensed community list** and cite it explicitly. Several maintained lists exist on GitHub with permissive licenses; pick one, pin the version, and record its provenance in the pack manifest.
2. **Derive N-levels from the old 1–4 scale plus frequency and jōyō grade** using a documented heuristic. Reproducible, but a guess.
3. **Ship both** — mark each sticky's JLPT tag with its source, and let the deck description say plainly: *"JLPT levels are community estimates. The Japan Foundation does not publish official lists."*

**Requirement:** the built-in JLPT deck descriptions must state the source and its unofficial status. Do not present estimates as fact. Allow users to correct a sticky's JLPT tag locally.

### 5.1 School grade and jōyō decks

These are unambiguous and come straight from KANJIDIC2's `grade` field:

| Deck | KANJIDIC2 grade |
|---|---|
| School Grade 1–6 | `grade` 1–6 |
| School Grade 7–9 (secondary) | `grade` 8, partitioned by frequency into three tiers to mirror StickyStudy's KK4/KK3/KK2.5 split |
| Jōyō (2010) | `grade` 1–8 (2,136 characters) |
| Jōyō (1981) | 2010 list minus the 196 added characters, plus the 5 removed |
| Top 500 Kanji | `freq` 1–500 |

The 1981/2010 diff (196 added, 5 removed) is a small hardcoded list — include it in the repo as a reviewed data file with a citation.

## 6. SKIP — what we cannot have

StickyStudy offers SKIP (System of Kanji Indexing by Patterns) search. **We cannot.**

SKIP is copyrighted by Jack Halpern / the Kanji Dictionary Publishing Society. Although SKIP codes appear inside KANJIDIC2, they carry their own separate terms: commercial or non-commercial use requires **written permission**, the data must be **encrypted** in any product, and it **must not be redistributed to third parties**. Encryption and non-redistribution are fundamentally incompatible with an open-source project whose data packs are public files.

**Decisions:**
- Strip all SKIP and SKIP-misclassification fields from our KANJIDIC2 extraction at build time. Add a pipeline assertion that fails the build if a SKIP field survives into a pack.
- Replace the capability with **multi-radical search** (KRADFILE/RADKFILE, CC BY-SA 4.0) plus stroke-count filtering. For finding an unknown kanji, multi-radical search is arguably better anyway.
- If someone wants SKIP, the path is: obtain written permission from the rights holder for a specific distribution arrangement. Document this as a standing wishlist item; do not block MVP on it.

Same reasoning applies to Halpern's frequency codes and to Heisig index numbers (*Remembering the Kanji* keywords and ordering are copyrighted by James Heisig / University of Hawai'i Press — an RTK deck is **not** shippable, though a "sort by RTK order" feature using only the index numbers is a grayer area worth avoiding entirely for MVP).

## 7. Similar-looking kanji — we generate this

StickyStudy's "similar looking kanji" display is one of its best features and there's no open dataset for it. We build one at pipeline time and publish it under CC BY-SA 4.0.

**Method:**
1. From KanjiVG, extract each character's component set (`kvg:element` values in its decomposition tree) and stroke count.
2. Compute a candidate set: characters sharing ≥1 non-trivial component, or within ±1 stroke and sharing the same radical.
3. Rasterize both characters at 64×64 from a common font and compute an image distance (normalized cross-correlation, or a small perceptual hash). This catches visual confusion that component analysis misses (己/已/巳, 未/末, 士/土).
4. Score = weighted blend of component overlap, stroke-count proximity, radical identity, and pixel similarity.
5. Keep the top 6 per character above a threshold.
6. **Manually review the top 200 most frequent kanji's lists.** The generated set will have obvious misses and obvious false positives; a few hours of human curation makes this feature feel hand-made.

Ship as `similar.json`: `{ "未": ["末","味","妹","昧"], ... }`. Publish the generator script.

## 8. Audio — the honest gap

StickyStudy ships 8,000+ words recorded by a human speaker. **There is no openly-licensed equivalent at that scale**, and the commonly-scraped sources (JapanesePod101, Forvo) are proprietary and cannot be redistributed. Do not scrape them. Do not link to a scraped mirror. This is the one place where KanjiForge will be genuinely worse than StickyStudy, and that's acceptable.

**Tiered plan:**

1. **Device speech synthesis (MVP).** `SpeechSynthesis` with a `ja-JP` voice. Available on iOS, Android, macOS, and Windows. Zero bytes shipped, zero licensing risk, universal coverage. Quality on modern iOS and Android is decent. Label it in the UI as synthesized so users aren't misled about pitch accent accuracy.
   - Implementation caveat: iOS requires `speechSynthesis.speak()` to originate from a user gesture on first use, and the voice list populates asynchronously. Handle both.
2. **Optional community audio packs (v1.1).** Define an open pack format: a zip containing `manifest.json` (mapping `writing|reading` → filename, plus license and attribution metadata) and audio files. Users can install packs; the project can host packs that have clean licenses.
3. **Project-rendered neural TTS pack (v1.2).** Pre-render the ~10k most common words using an open-licensed Japanese TTS engine, checking the specific voice model's terms. Ship as a downloadable pack, ~150 MB. Higher and more consistent quality than device TTS, at the cost of a large download.
4. **Wikimedia Commons pronunciations.** Some Japanese word audio exists under CC licenses on Commons. Coverage is sparse and inconsistent in quality — worth harvesting into a pack as a supplement, not a foundation.

## 9. Fonts

| Font | Role | License |
|---|---|---|
| Noto Sans JP | UI, readings, list text | SIL OFL 1.1 |
| Noto Serif JP | Large card character (明朝 forms) | SIL OFL 1.1 |
| Klee One | Alternate card face — textbook/handwriting forms, matches how kanji are taught | SIL OFL 1.1 |
| (Latin display + body faces) | Headings and glosses | Choose OFL-licensed; see PRD §6.3 |

**Subsetting is mandatory.** Full Noto Sans JP is ~5 MB per weight. Build a subset containing:
- The jōyō + jinmeiyō set plus every character appearing in any bundled deck or in `words-core` (roughly 3,500 characters)
- Full kana, punctuation, and Latin/digits

Use `unicode-range` splitting across several woff2 chunks so the browser fetches only what it renders. Target ≤400 KB for the initial Japanese font payload.

Do **not** rely on system Japanese fonts. Android device coverage is inconsistent, and the whole point of a kanji app is that the character renders correctly at 200px.

## 10. Tokenization (for the text analyzer, v1.1)

| Option | Notes |
|---|---|
| **Kuromoji.js** + IPADIC | Apache-2.0, pure JS, ~15 MB dictionary, well-proven, slow-ish first load. The safe default. |
| **Lindera-wasm** + IPADIC/UniDic | Rust compiled to WASM. Faster, smaller memory footprint, more modern. Check the exact dictionary license (IPADIC is BSD-like; UniDic has its own terms). |
| Server-side MeCab | ❌ Rejected. Breaks the offline requirement and the no-server principle. |

Whichever is chosen, the tokenizer dictionary is a **separately downloadable content pack**, only fetched when the user first opens the text analyzer. It must never be in the critical path for study.

## 11. Build pipeline requirements

The pipeline lives in `scripts/build-packs/` and must be:

- **Reproducible** — every upstream source pinned to a specific release tag or dated snapshot, with a checksum recorded in `sources.lock.json`. A build from the same lock file produces byte-identical packs.
- **CI-runnable** — a scheduled workflow refreshes upstream sources monthly, rebuilds, runs assertions, and opens a PR with the diff.
- **Reproducibility modes** — pull-request CI validates the committed pack fixture and its assertions. The authoritative reproducibility check runs on the monthly scheduled refresh after it has fetched the full locked cache: it executes the kanji, words-core, strokes, sentences, similar, and decks builders twice in separate output workspaces using that same cache, writes deterministic Brotli publication artifacts, and byte-compares every generated file. It is intentionally not a synthetic fixture generator. The committed fixture currently validates assertions only; it is not an authoritative builder-reproduction input.
- **Assertive** — the build fails, loudly, if:
  - Any SKIP or misclassification field appears in output
  - Any source's license file hash changed since the lock
  - Kanji count, word count, or sentence count moves more than 5% from the previous build
  - Any pack exceeds its declared size budget
  - Any output pack lacks a `license` and `attribution` field in its manifest
- **Versioned** — each pack has `{ id, version, schemaVersion, sha256, sizeBytes, license, attribution, sources[] }`. The app checks `schemaVersion` compatibility before installing.

### 11.1 Output format

Publish each pack as:
- A **SQLite database file** for anything queried (words, kanji, sentences, radicals) — queried in-browser via SQLite-WASM over OPFS, giving real indexed search and full-text search offline without loading everything into memory.
- **JSON** for small lookup tables (similar kanji, radical grid, deck definitions).
- **Binary/JSON** for stroke paths, chunked by Unicode block so a user studying grade 1 kanji doesn't download stroke data for all 6,500.

Compress with Brotli. Serve with long-lived immutable cache headers keyed on the version hash.

## 12. Attribution deliverables

Three artifacts, all required before first public release:

1. **`ATTRIBUTION.md`** in the repo — full text of each license plus a per-source statement of what was used and how it was modified.
2. **In-app "Data sources" screen** — Settings → About → Data sources. Lists each source with author, license name, license link, and a one-line description. Must be reachable without network.
3. **Per-pack manifest metadata** — so a pack is self-describing even if separated from the app.

Draft attribution block for the About screen:

> KanjiForge is built on open Japanese language data.
>

## 13. What we deliberately do not use

| Source | Why not |
|---|---|
| SKIP codes | Requires written permission + encryption; incompatible with open distribution |
| Heisig RTK keywords/ordering | Copyrighted; a shipped RTK deck is not defensible |
| JapanesePod101 / Forvo audio | Proprietary; scraping is not an option |
| NHK News Web Easy content | Copyrighted news text. If a news feature is ever built, it must link out rather than reproduce, or use CC-licensed sources (e.g. Japanese Wikinews, CC BY 2.5) |
| WaniKani mnemonics/radical names | Proprietary |
| Any scraped commercial dictionary | Obvious |
| Google/DeepL translation APIs | Breaks offline-first and no-server principles; also cost |
