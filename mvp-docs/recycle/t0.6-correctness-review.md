# Correctness & Logic Review

**Task:** T0.6 Tatoeba → sentences pack ETL  
**Worktree:** `.claude/worktrees/t0.6-sentences-etl`  
**Branch tip:** `e45b69c` (uncommitted builder/pack/docs on worktree)  
**Scope:** `scripts/build-packs/build-sentences-pack.ts`, `packs/sentences-v1.manifest.json`, `mvp-docs/t0.6-done-check.md`  
**Spec:** `DATA-SOURCES.md` §4.1–4.2; ORCHESTRATION T0.6 (JA+EN, length 6–30, ≤5 per word, furigana, sense-linked via indices, CC BY 2.0 FR)

## Summary

The builder produces a multi-MB pack with real JA/EN pairs, length filtering, and a readability ranker — a clear step past the prior stub. However, several logic bugs mean the pack does **not** meet the core T0.6 contract: sense-linked examples for JMdict meanings, ≤5 sentences per word, and correct furigana. The WWWJDIC parser misreads `(#ent_seq)` and drops or mangles many tokens; the ≤5 cap is applied only when choosing which sentences to keep, then **all** word links on kept sentences are re-emitted (so common senses far exceed 5); furigana often stores the dictionary lemma as ruby text for conjugated surfaces; and the manifest mislabels JmdictFurigana as MIT / pack-only CC BY 2.0 FR despite CC BY-SA upstream. Done-check samples themselves demonstrate broken furigana (`になりました` → `になる`).

## Issues

### 1. WWWJDIC `(#ent_seq)` ignored — JMdict sense join is broken
**File**: `scripts/build-packs/build-sentences-pack.ts` (lines 136–152, 417–418, 453)  
**Concern**: Tatoeba’s indices routinely encode the real JMdict entry id as `(#NNNNNNN)`, e.g. `が(#2028930)`, `前(#1392580)[02]`, `施行(#1579510)`. The parser treats **any** `(…)` as a kana reading (`parenMatch`), never extracts `#ent_seq`, and stores `jmdict_sense_id` as `` `${surface}:${senseNum}` `` (e.g. `２０歳:01`). That key cannot join to `words-core` / `words-full`, which key entries by `ent_seq` (see `build-words-core-pack.ts`). Spec §4.1: indices exist so the app can show examples for *this meaning of this word*.

Concrete failures on real cache tokens:
- `が(#2028930)` — no `{}`, no `[nn]` → token **dropped entirely** (neither branch runs).
- `前(#1392580)[02]` — sense branch sets `surface = "前(#1392580)"` (parens not stripped) → `ja.indexOf` fails → no link / bad highlight.
- `猫(ねこ)[01]` — surface becomes `"猫(ねこ)"` → position match fails.

**Suggestion**: Parse tokens into `{ headword, reading?, entSeq?, senseNum, surface }`:
```ts
// (#1234567) → entSeq; (かな) → reading; [02] → sense; {表層} → surface; else surface = headword
const entSeqMatch = tok.match(/\(#(\d+)\)/);
const readingMatch = tok.match(/\(([^)#][^)]*)\)/); // kana reading, not #id
```
Store `jmdict_sense_id` as `` `${entSeq}:${senseNum}` `` when `entSeq` is present; otherwise resolve headword→ent_seq via JMdict forms at build time. Never put `(#…)` into `reading` or into the searchable surface.

### 2. ≤5-per-word cap is not enforced on final links
**File**: `scripts/build-packs/build-sentences-pack.ts` (lines 429–459)  
**Concern**: Cap logic takes the top-5 sentence ids **per sense key**, unions them into `keptSentenceIds`, then rebuilds `wordLinks` for **every** indexed word on every kept sentence:

```ts
for (const word of indicesEntry.words) {
  // pushes a link for this word even if this sentence was only kept for a different sense
}
```

So if sentence S is kept because it is top-5 for rare word X, and S also contains common word Y, S is still linked to Y. Querying `sentence_word_links` by Y’s key returns far more than 5 rows. Spec / ORCHESTRATION: “≤5 per word, ranked by readability.” Done-check’s claim that GROUP BY shows ≤5 is inconsistent with this control flow (unless verification was run only on the pre-union candidate map).

**Suggestion**: Persist only the `(senseKey, sentenceId)` pairs that survived that sense’s top-5 slice:
```ts
const keptLinks = new Set<string>(); // `${senseKey}\t${sentenceId}`
// when taking top5: keptLinks.add(`${senseId}\t${c.sentenceId}`)
// when building wordLinks: only push if keptLinks.has(...)
```
Optionally still keep the sentence row for multi-word display, but do not index excess senses.

### 3. Cap key uses conjugated surface, not dictionary word
**File**: `scripts/build-packs/build-sentences-pack.ts` (lines 140–145, 417–418)  
**Concern**: Sense bucket is `` `${word.kanji}:${word.senseId}` `` where `kanji` is the **surface** from `{}` (e.g. `なりました`, `書いている`). Spec says cap per **word**. Conjugations of the same headword get separate 5-buckets (`なる` vs `なりました` vs `なって`), so one lemma can keep many more than 5 examples, while each surface fragment is under-capped. Combined with issue 1, keys are also not stable headword/sense ids the app can query from a word detail screen.

**Suggestion**: Bucket and store by headword (lemma before `{}`) + sense (and ent_seq when present), e.g. `成る:01` / `1157170:01`. Keep surface only for highlight offsets.

### 4. Furigana stores dictionary lemma on conjugated surfaces (sample is wrong)
**File**: `scripts/build-packs/build-sentences-pack.ts` (lines 140–145, 319–327); evidenced in `mvp-docs/t0.6-done-check.md` (lines 56–58)  
**Concern**: For `になる[01]{になりました}` the parser sets `reading = lemma` (`になる`) because there is no `(kana)` group. Fallback furigana then does:
```ts
segments.push({ text: wordSurface, furigana: word.reading }); // text=なりました, furigana=になる
```
Done-check’s own “real” sample shows exactly this:
`{"text":"になりました","furigana":"になる"}` — invalid ruby (lemma ≠ reading of the surface). JmdictFurigana is a **word** aligner (project README: not for sentences / conjugated forms); looking up `なりました|になる` will miss. Target-word highlight + furigana done-check therefore fails on a documented sample.

**Suggestion**:
- Prefer JmdictFurigana on **headword|trueReading** (from `(かな)`), then map ruby onto the kanji stem of the surface; leave okurigana/conjugation tails as plain kana with empty `rt`.
- Never use the dictionary lemma string as `furigana` for a different surface.
- If no safe alignment, emit `{ text: surface, furigana: "" }` rather than a wrong reading.

### 5. `applyFurigana` corrupts segment stream when surface is not found
**File**: `scripts/build-packs/build-sentences-pack.ts` (lines 330–334)  
**Concern**: When `indexOf(wordSurface, pos) === -1` (common once surfaces still contain `(…)`, fullwidth drift, or `~` markings), the code still pushes the missing surface and advances `pos` by `wordSurface.length` without consuming real sentence characters:
```ts
} else {
  segments.push({ text: wordSurface, furigana: word.reading || '' });
  pos += wordSurface.length; // invents characters; desyncs the rest
}
```
Concatenating `furigana_json[].text` no longer equals `ja`. Any UI that trusts segments for layout/highlight will mis-render the rest of the sentence.

**Suggestion**: On miss, skip the token (or log), do **not** advance `pos` by surface length, and never insert text that is not a slice of `ja`. Assert `segments.map(s => s.text).join('') === ja` before insert.

### 6. Tokens without `{}` or `[nn]` are dropped; bare headwords never linked
**File**: `scripts/build-packs/build-sentences-pack.ts` (lines 140–152)  
**Concern**: Only tokens with `{surface}` or `[sense]` enter `words`. Plain content words with only `headword(reading)` (e.g. `先生(せんせい)`, `は`, `の`) are ignored. Combined with issue 1, many high-value content tokens that only carry `(#ent_seq)` also vanish. Link coverage is systematically incomplete relative to the indices file.

**Suggestion**: Default branch: strip `(…)`, `[…]`, `~`, `^`; surface = headword (or `{}` if present); always emit a word record when a non-empty headword/surface remains. Skip only true noise tokens (`NI{…}` if undesired, empty after strip).

---

### 7. PRIMARY KEY drops repeated same-sense hits in one sentence
**File**: `scripts/build-packs/build-sentences-pack.ts` (lines 487–494, 522–524)  
**Concern**: `PRIMARY KEY (sentence_id, jmdict_sense_id)` + `INSERT OR IGNORE` keeps only the first offset when the same sense appears twice (e.g. repeated verb in `寝る{寝ても} 寝る{寝ても}`). Second highlight span is lost. Highlight UI cannot mark both occurrences.

**Suggestion**: Use a surrogate PK or `(sentence_id, word_start_char)` and allow multiple rows per sense; or store a JSON array of spans per sense.

### 8. Manifest license wrong for JmdictFurigana / pack mixture
**File**: `packs/sentences-v1.manifest.json` (lines 7–8, 21–22); builder lines 551–567  
**Concern**:
- Upstream JmdictFurigana README: *“distributed under the same licence as JMDict (Creative Commons Attribution-ShareAlike Licence).”*
- `DATA-SOURCES.md` summary table and §4.2: CC BY-SA (verify).
- `fetch-sources.ts` pins license `CC BY-SA 4.0`.
- This pack’s manifest labels JmdictFurigana as **`MIT`** and the pack license as **`CC BY 2.0 FR` only**.

Embedding SA furigana alignments into a pack declared “CC BY 2.0 FR (no share-alike)” misstates terms and fights §4.1’s reason for shipping sentences separately from EDRDG packs. Done-check repeats the MIT claim.

**Suggestion**: Label JmdictFurigana `CC BY-SA 4.0` (or current verified SPDX). Either (a) dual-license / mark the pack as containing SA-derived furigana fields, or (b) ship furigana in a separate SA pack and keep pure Tatoeba rows under CC BY 2.0 FR. Recompute attribution text accordingly.

## No blockers outside correctness scope

Architecture/style (streaming design, sql.js usage, path layout) are out of scope. Size vs “~12 MB packed” is acceptable if Brotli is applied at serve time (§11.1); flag only if CI asserts uncompressed budget.

## Recommended fix order

1. Rewrite WWWJDIC token parse (ent_seq / reading / surface / headword) — unblocks join + positions.  
2. Cap and store links only for top-5 `(sense → sentence)` pairs; key by ent_seq:sense or headword:sense.  
3. Fix furigana fallback; add reconstruct-equals-`ja` assert.  
4. Correct manifest licenses + stats from DB.  
5. Re-run full build; replace done-check samples with verified rows.
