# Correctness & Logic Review

**Task:** T0.5 KanjiVG → strokes pack ETL  
**Scope:** `scripts/build-packs/build-strokes-pack.ts`, `packs/strokes/manifest.json`, sample chunk outputs  
**Specs:** DATA-SOURCES §3, ARCHITECTURE §5/§8 (stroke assets feed animation/validation later), ORCHESTRATION T0.5  
**Date:** 2026-07-25

## Summary

The builder correctly pins KanjiVG `r20260714`, emits a **separate** strokes pack with **CC BY-SA 3.0** (not 4.0), and for simple samples the ordered `paths` / `startPoints` look right (e.g. 一=1, 丁=2 paths with matching M-start coordinates; KanjiVG SVGs for 川/本/言 are 3/5/7 strokes). License and attribution strings match DATA-SOURCES §3.2.

However, the component “tree” is not a tree (flat + deduped), rebuilds leave **stale overlapping chunk files** beside the new scheme, chunk/key ordering is filesystem-order nondeterministic (manifest SHA not stable), and several defensive path/start-point edge cases can desynchronize `paths[i]` from `startPoints[i]`. These are real correctness bugs for detail “elements”, T0.7 similar-kanji, and any consumer that globs `packs/strokes/*.json`.

## Issues

### 1. Component decomposition is a flat unique set, not a parent/child tree
**File**: `scripts/build-packs/build-strokes-pack.ts` (lines 140–169)  
**Concern**: `parseComponentTree` scans every `<g kvg:element="…">` in the SVG, skips only the root element string, and pushes **unique** element names into a single `children` array (`processedElements` Set). That fails DATA-SOURCES §3.1 #3 (“parent/child tree of `kvg:element` values”) in three ways:

1. **No nesting.** Nested structure is flattened. For 本 (KanjiVG: `本 → 木 → 丨`), the pack would emit `children: [木, 丨]` instead of `木` containing `丨`. For 語 (`語 → 言 → 口` and `語 → 吾 → …`), `口`/`五`/`二` become siblings of `言`/`吾`.
2. **Duplicate components dropped.** Characters with repeated elements lose multiplicity. 東 has two `木` parts (`kvg:part="1"` and `"2"`); the Set keeps only one `木`. 語 has two `口` and two `二` parts — each appears once.
3. **Part / position / original metadata discarded.** Split radicals (`kvg:part`), positions, and `kvg:original` (e.g. 川’s `kvg:original="巛"`, 亻’s original 人) are ignored, so T0.7 component-overlap scoring and detail “elements” get a distorted set.

Done-check claims trees like 丁 → `[亅]` only; live `strokes-4E00-4FFF.json` actually has 丁 → `[一, 亅]` (flat), which already shows the “all descendant elements as children” behavior.

**Suggestion**: Parse only the main `kvg:StrokePaths_*` group, walk nested `<g>` nodes recursively, and emit a real tree. Preserve repeated siblings; optionally keep `part` / `position` / `original` if useful for T0.7. Sketch:

```ts
function parseGroup(gXml: string): ComponentNode {
  const element = /* kvg:element on this g */;
  const children = /* direct child <g kvg:element> only, each parseGroup(...) */;
  return children.length ? { element, children } : { element };
}
```

Do not dedupe by element string.

### 2. Stale chunk files from prior split left on disk (overlapping Unicode coverage)
**File**: `scripts/build-packs/build-strokes-pack.ts` (`writeChunks`, ~269–337); `packs/strokes/`  
**Concern**: `writeChunks` only writes the current scheme’s filenames. It never clears `packs/strokes/` first. On disk after the “5-way” retarget, **both** schemes coexist:

| Stale (older run) | Current (manifest) |
|---|---|
| `strokes-4E00-4E1F.json` | `strokes-4E00-4FFF.json` |
| `strokes-4E20-5FFF.json` | `strokes-5000-5FFF.json` |
| `strokes-6000-74FF.json` | `strokes-6000-6FFF.json` |
| `strokes-7500-9FFF.json` | `strokes-7000-7FFF.json` / `strokes-8000-9FFF.json` |
| `strokes-CJK_Extended.json` (rewritten) | same name |

`manifest.json` lists only the new six files, but any loader that globs `strokes-*.json` (or trusts directory listing) will load **duplicate codepoints** with conflicting chunk membership (e.g. U+4E00 in both `4E00-4E1F` and `4E00-4FFF`). That is a data-integrity footgun for pack install and offline cache.

`t0.5-done-check.md` still documents the **old** filenames/sizes, so verification artifacts disagree with the live manifest.

**Suggestion**: Before writing, delete existing `strokes-*.json` in `OUTPUT_DIR` (or write to a temp dir and rename atomically). Align done-check with the files named in `manifest.json`. Prefer consumers that **only** fetch `manifest.chunks[].filename`.

### 3. Chunk and key order are nondeterministic → unstable manifest `sha256`
**File**: `scripts/build-packs/build-strokes-pack.ts` (lines 188–219, 242–266, 285–329, 351–358)  
**Concern**:

- Characters are inserted into `strokes` Map in `fs.readdirSync` order (not codepoint order).
- `groupByUnicodeBlock` inserts block keys in **first-seen** order, not `UNICODE_BLOCKS` order.
- `writeChunks` / `createManifest` iterate those Maps as-is; JSON object key order follows insertion order; combined pack `sha256` hashes chunk hash strings in that order.

`manifest.json` currently lists `CJK_Extended` **first**, which is a smell that extended-plane files appeared before U+4E00 in readdir — order will differ across OS/filesystems and possibly across runs. CI “hash locked” checks and content-addressed caching will flake even when logical content is identical.

**Suggestion**: After parse, sort each block’s entries by numeric codepoint; emit chunks in fixed `UNICODE_BLOCKS` order then `CJK_Extended`; build objects by inserting keys in sorted order (or use a stable stringify). Recompute manifest hashes after that.

### 4. `startPoints` can desync from `paths` when a path fails M-parse
**File**: `scripts/build-packs/build-strokes-pack.ts` (lines 97–107, 209–211)  
**Concern**:

```ts
const startPoints = paths
  .map((p) => extractStartPoint(p))
  .filter(Boolean) as Array<{ x: number; y: number }>;
```

If any path’s `d` does not match `/M([\d.-]+)[,\s]+([\d.-]+)/`, that entry is **dropped**, so `startPoints.length < paths.length` and `startPoints[i]` no longer corresponds to `paths[i]`. Writing trainer / StrokePlayer (PRD numbered start-points; ARCHITECTURE §8 `startDist`) will hint the wrong stroke.

KanjiVG samples reviewed use absolute `M` without a space after `M` (e.g. `M14,24.17`), so today’s corpus likely parses — but the contract is index-aligned arrays, and the filter silently breaks that contract. Also unhandled: leading space after `M` (`M 14,24`), relative `m`, or more exotic number forms.

**Suggestion**: Keep 1:1 alignment; fail the character (or use a sentinel and log) instead of filtering:

```ts
const startPoints = paths.map((p, i) => {
  const pt = extractStartPoint(p);
  if (!pt) throw new Error(`No start point for ${codepointHex} stroke ${i}`);
  return pt;
});
```

Harden the regex (optional space after `M`/`m`, allow exponent if needed).

### 5. Claimed 109×109 “normalization” is not implemented
**File**: `scripts/build-packs/build-strokes-pack.ts` (lines 6–7, 116–118, 137); manifest attribution  
**Concern**: `viewBox` is extracted and then **discarded**. Paths are copied verbatim. ORCHESTRATION T0.5 / DATA-SOURCES §3.1 require “normalized ordered stroke `d`-strings (109×109)”. Attribution states “Paths normalized and re-encoded.”

Current KanjiVG release SVGs checked (`04e01`, `05ddd`, `0672c`, `08a00`, …) already use `viewBox="0 0 109 109"`, so output coordinates happen to be correct **if and only if** every file stays on that convention. There is no assert and no transform if a file differs (or if a future pin changes).

**Suggestion**: Assert `viewBox === "0 0 109 109"` (or parse and scale/translate path coordinates into that box). If pass-through is intentional, drop “normalized and re-encoded” from attribution or document “verified already 109×109; copied as-is.”

### 6. Paths collected from entire SVG, not only `StrokePaths` group
**File**: `scripts/build-packs/build-strokes-pack.ts` (lines 126–132)  
**Concern**: Global `/<path[^>]*d="([^"]*)"/g` walks the whole file. Today StrokeNumbers are `<text>`, so stroke counts match KanjiVG for samples — but any future/nonstandard path outside `kvg:StrokePaths_*` (guides, decorations, alternate layers) would inflate stroke order and break animation/validation.

Stroke order currently relies on document order equaling `…-s1`, `…-s2`, … which holds for standard KanjiVG but is not enforced via `id` / stroke index sort.

**Suggestion**: Restrict path extraction to the `id="kvg:StrokePaths_…"` subtree (or only paths whose `id` matches `/kvg:[0-9a-f]+-s\d+/`). Optionally sort by stroke index from the id for defense in depth.

### 7. Done-check / “5 chunk files” disagrees with builder output
**File**: `mvp-docs/t0.5-done-check.md` (lines 29–57); `packs/strokes/manifest.json`  
**Concern**: Not a runtime bug by itself, but it masks pack correctness:

- Done-check lists **old** ranges (`4E00-4E1F`, `4E20-5FFF`, `6000-74FF`, `7500-9FFF`) and sizes (~9.09 MB old total).
- Live manifest lists **new** ranges (`4E00-4FFF` … `8000-9FFF` + `CJK_Extended`) and `sizeBytes: 9485197` across **6** chunk entries.
- Narrative says “5 files total” while the builder always emits 5 CJK blocks **+** Extended.

Reviewers or CI copying done-check expectations will validate the wrong artifacts.

**Suggestion**: Regenerate done-check from the current manifest only; say “5 CJK blocks + Extended catch-all (6 chunk files).”

## What looks correct

- **License separation:** `license: "CC BY-SA 3.0"` and attribution match DATA-SOURCES §3.2–§3.3; not merged into 4.0 EDRDG packs.
- **Source pin:** Zip name / manifest `pinned: "r20260714"` aligns with `sources.lock.json` kanjivg entry.
- **Variant skip:** Filenames containing `-` (style variants) are skipped — correct for a single canonical stroke order per codepoint.
- **Sample path/start data (spot-check):** `04e00` (一) has 1 path and `startPoints: [{x:11,y:54.25}]` matching `M11,54.25…`; `04e01` (丁) has 2 paths/starts matching upstream SVG. Upstream 川/本/言 stroke counts are 3/5/7 as claimed.
- **Unicode range math:** Half-open intervals `[start, end)` with labels `4E00-4FFF` … `8000-9FFF` are consistent (e.g. U+9FFF included via `end: 0xa000`).
