# Correctness & Logic Review

**Task:** T0.4 — words-core ETL  
**Worktree:** `.claude/worktrees/t0.4-words-etl`  
**Branch:** `t0.4-words-etl`  
**Reviewed:** working tree (uncommitted better-sqlite3 + FTS5 builder) + `packs/words-core-v1.*`  
**Specs:** `DATA-SOURCES.md` §2.2–2.3, §11.1; `ARCHITECTURE.md` §4.1; `ORCHESTRATION.md` T0.4

## Summary

The builder’s shape matches the intended T0.4 design: `*_pri` filter, `entries` / `forms` / `glosses_fts` schema, packed JSON BLOBs, derived `common_score`, and a real ~30k-entry pack with offline FTS. Entry/form/gloss counts are in the right ballpark for JMdict priority-tagged vocabulary. However, the line-oriented regex parser does **not** resolve JMdict DTD entities, so POS/misc/field/inf tags and some gloss/form text are stored in encoded form — a data-integrity bug that will break display and can break search. Several pipeline integrity gaps (hardcoded source path, no lockfile hash check, non-atomic outputs, no Brotli size proof) remain.

## Issues

### 1. JMdict DTD / character entities are not decoded
**File**: `scripts/build-packs/build-words-core-pack.ts` (lines 110–214, 350–364)  
**Concern**: JMdict_e is DTD-backed XML. Tags such as `<pos>&n;</pos>`, `<misc>&uk;</misc>`, `<ke_inf>&ateji;</ke_inf>`, `<field>&comp;</field>` are stored literally as `&n;`, `&uk;`, etc. Character entities in text (`&amp;`, `&quot;`, `&apos;`, numeric refs) are likewise left encoded in `keb` / `reb` / gloss strings.

A non-validating regex parser never expands the DOCTYPE entity table, so the packed JSON BLOB and FTS index do not contain the values a real XML parse would produce. Runtime impact:

- Detail UI will show raw entities (`&n;`) unless every consumer re-implements the JMdict entity map.
- Gloss FTS for strings containing `&` / quotes can miss (e.g. stored `AT&amp;T` vs query `AT&T`).
- §2.2 requires extracting `pos`, `misc`, `field`, `dial`, `ke_inf`, glosses — encoded forms are not faithful extractions.

**Suggestion**: Either (a) parse with a DTD-aware XML parser, or (b) load JMdict’s entity list once and run a decode pass on every captured text node before insert:

```ts
function decodeJmdictEntities(s: string, entityMap: Record<string, string>): string {
  return s
    .replace(/&([a-zA-Z0-9.-]+);/g, (_, n) => entityMap[n] ?? `&${n};`)
    .replace(/&#x([0-9a-fA-F]+);/g, (_, h) => String.fromCodePoint(parseInt(h, 16)))
    .replace(/&#([0-9]+);/g, (_, d) => String.fromCodePoint(parseInt(d, 10)));
}
```

At minimum, always decode the five XML predefined entities (`&amp; &lt; &gt; &quot; &apos;`) on keb/reb/gloss, and strip/map POS-like entities to their short codes or replacement text.

### 2. Failed rebuild can leave partial DB + stale manifest (hash mismatch)
**File**: `scripts/build-packs/build-words-core-pack.ts` (lines 296–300, 302, 398, 412–439)  
**Concern**: Build deletes any existing DB, opens a new file immediately, streams inserts, then writes the manifest. If the process throws mid-insert:

1. `packs/words-core-v1.sqlite` is a **partial** database.
2. `packs/words-core-v1.manifest.json` is **not** rewritten, so it still carries the previous run’s `sha256` / `stats`.

Installers that trust the manifest will accept a corrupt/partial pack (hash won’t match) or reject a good later manual swap. This is a real data-integrity failure mode on interrupted CI/local builds.

**Suggestion**: Write to temp paths and rename atomically; clear or rewrite the manifest at the start of a build; only publish manifest after DB close + hash of the final file:

```ts
const tmpDb = OUTPUT_DB + '.tmp';
// ... build into tmpDb ...
fs.renameSync(tmpDb, OUTPUT_DB);
await writeManifest(stats);
```

### 3. Source path is hardcoded; lockfile SHA is never checked
**File**: `scripts/build-packs/build-words-core-pack.ts` (lines 47–50, 447–450)  
**Concern**:

- Input is fixed to `scripts/build-packs/.cache/jmdict-2026-07-25.gz`.
- `sources.lock.json` pins `jmdict.pinned = "2026-07-25"` and a `sha256`, but the builder does not read the lockfile or verify the file hash.

Failure scenarios:

- Re-fetch with a new pin date → builder exits “source not found” until the constant is hand-edited.
- Wrong/corrupt/truncated cache file with the expected name → silent bad pack (counts may still look plausible).

DATA-SOURCES intro explicitly requires failing the pipeline when upstream integrity is wrong.

**Suggestion**: Resolve path from lockfile (`${id}-${pinned}.gz`) and assert `sha256(file) === lock.sources.jmdict.sha256` before parse.

### 4. `*_pri` filter ignores `nfXX` frequency tags
**File**: `scripts/build-packs/build-words-core-pack.ts` (lines 55–65, 263–288, 339–344)  
**Concern**: DATA-SOURCES §2.3 / ORCHESTRATION T0.4 say words-core = entries with **any** `*_pri` tag. JMdict also emits `nf01`–`nf48` as `ke_pri` / `re_pri` values. `PRI_SCORE` only lists `news*`, `ichi*`, `spec*`, `gai*`. An entry whose only priority markers are `nfXX` gets `score === 0` and is dropped.

In practice most `nfXX` rows also carry `news1`/`news2`, and the ~30146 count matches the usual ~30k band — so impact may be small or zero today — but the filter is not literally “any `*_pri`”. `is_common` (lines 371–378) treats any non-empty pri list as common (including `nfXX`), which is inconsistent with scoring.

**Suggestion**: Treat any non-empty `ke_pri`/`re_pri` as inclusion, and optionally fold `nfXX` into `common_score` (e.g. `50 - parseInt(nf, 10)` capped) for finer ranking within news bands:

```ts
function priRank(pri: string): number {
  if (pri in PRI_SCORE) return PRI_SCORE[pri];
  const m = /^nf(\d{2})$/.exec(pri);
  if (m) return 20 + (48 - parseInt(m[1], 10)); // nf01 highest among nf
  return 1; // unknown pri still counts as "any *_pri"
}
```

### 5. Done-check size budget (`≤ ~6 MB compressed`) is not met or verified
**File**: `mvp-docs/t0.4-done-check.md` (lines 37–38); missing artifact under `packs/`  
**Concern**: ORCHESTRATION T0.4 done-check requires `words-core` ≤ ~6 MB **compressed**. Delivered artifact is raw SQLite at ~26 MB (`sizeBytes: 27234304`). No `.br` (or other) compressed pack is produced, and nothing asserts Brotli size ≤ 6 MB.

This is a release-gate / correctness-against-spec miss: the pack may still exceed budget after compression (JSON-in-BLOB + full sense arrays + FTS index is heavy).

**Suggestion**: Emit `words-core-v1.sqlite.br` (or compress in the publish step), record compressed size in the manifest, and fail the build if over budget. Consider stripping empty sense fields and/or FTS `detail=none` / content-less FTS if size overshoots.

### 6. Empty gloss rows can be inserted when the gloss regex fails
**File**: `scripts/build-packs/build-words-core-pack.ts` (lines 202–214, 384–390)  
**Concern**: On a `<gloss...>` line, if `>([^<]*)<` does not match, `text` becomes `''` and is still pushed, then inserted into `glosses_fts` (empty string is truthy enough to pass the lang filter). Empty FTS rows waste space and can produce odd MATCH behavior.

**Suggestion**: Skip empty glosses after decode/trim:

```ts
const text = decode(textMatch?.[1] ?? '').trim();
if (!text) continue;
```

---

### 7. Parse-state flags are not reset on `</entry>` / `<entry>`
**File**: `scripts/build-packs/build-words-core-pack.ts` (lines 83–95, 104–109, 128–133, 166–171)  
**Concern**: Closing `</entry>` clears `inEntry` and `currentEntry` but not `inKEle` / `inREle` / `inSense` or the current child pointers. Official JMdict is well-formed so this is latent; a truncated line or future format glitch can leak state into the next entry (mis-attributed keb/gloss, or dropped fields).

**Suggestion**: Reset the full `ParseState` whenever an entry opens or closes.

### 8. `common_score` ranking is usable, but FTS alone is not “commonScore-ranked”
**File**: `scripts/build-packs/build-words-core-pack.ts` (lines 319, 333–334); `mvp-docs/t0.4-done-check.md` (lines 55–73)  
**Concern**: DATA-SOURCES §2.2 says commonality ranking drives **search result ordering**. The pack correctly stores `common_score` on `entries`, but `glosses_fts` inserts carry no rank signal; default FTS5 order is bm25/rowid unless the app joins and `ORDER BY common_score DESC, rank`. Done-check “ranked” samples do not show that join — easy for a later dictionary query to “forget” commonScore.

Not a pack schema bug (column exists), but the ETL/docs overclaim “ranked” FTS without documenting the required query shape.

**Suggestion**: Document the canonical search SQL in the builder header or a short `packs/README` snippet, e.g.:

```sql
SELECT e.id, e.common_score, f.gloss
FROM glosses_fts f
JOIN entries e ON e.id = f.entry_id
WHERE glosses_fts MATCH ?
ORDER BY e.common_score DESC, rank
LIMIT 50;
```
